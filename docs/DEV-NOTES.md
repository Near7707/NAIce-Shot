# NAIce Shot 개발 메모 (이어서 작업하는 사람용)

리뷰 지적을 확인하거나 고칠 때, 검사를 새로 쓸 때 보는 문서예요. 버전별로 무엇을 왜 고쳤는지는 [REVIEW.md](REVIEW.md)·[ROADMAP.md](ROADMAP.md)(각 버전 칸의 "규칙" 줄), 화면 규칙과 알려진 한계는 [DESIGN.md](DESIGN.md)가 기준이에요. 이 문서는 그 셋에 없는 "코드 구조 · 지적 종류별로 볼 곳 · 검사 쓰는 요령"을 모아 둔 곳이에요. 기준 버전: 0.1.162. 구조나 검사 도우미가 바뀌면 이 문서를 같이 고쳐 주세요.

## 1. 리뷰 지적 종류별로 볼 곳

공통 원칙: 같은 구조에서 지적이 또 나오면 땜질 전에 가장 가까운 공통 지점 한 곳에서 막기. 새 상태·잠금·큰 재작성은 피하기. 데이터가 사라지거나 다른 인물·다른 그림이 들어가는 경우만 고치고, 안내 문구만 틀리거나 표시가 잠깐 늦는 건 알려진 한계로 기록.

- **@ 목록 위치(0.1.154~0.1.157) 지적이 나오면:** (가로 화면 관련은 사용자가 신경 안 쓰기로 함 → ⚪ 추천) 위치는 `updateRefList` 한 곳. 순서: 가로 `left` → 보이는 화면 `seenTop/seenBottom`(visualViewport) → 칸이 화면 밖이면 닫기 → `maxHeight=''` 풀고 높이 `h` → 아래(`below`)에 다 들어가면 아래, 위(`above`)에 들어가면 위, 둘 다 아니면 넓은 쪽 + 자리 `room`(한 줄도 안 되면 닫기) → `maxHeight=room` → `want` → 실제 위치 보정 `off` → 선택 후보 스크롤(크면 맨 위). 다시 맞추는 때: 입력·클릭·방향키 keyup/keydown·패널 `.ncs-content` scroll·window resize·`visualViewport` resize/scroll. 보정은 세로만. 남은 ⚪: 확대 잘림(0.1.155 P3-2), 키보드 열리는 도중 닫힌 채(0.1.156 P3), 첫 후보가 키 크면 닫힘(0.1.157 P3). 아이폰에서만 생기는 건 시험 페이지로 먼저 재기.
- **알약 메뉴(0.1.158~0.1.162) 지적이 나오면:** 연결을 바꾸는 건 `pillAction` → chipfield `dropRef`(지우기, 뒤에서부터 자리마다)/`repickAll`(다시 고르기, 첫~끝 자리 새 글을 한 번에, 0.1.160) 둘뿐. 알약 쪽이 보는 연결은 모두 `field.refs()` = `counted()`(0.1.162, 가려진 연결 없음) — "겹친/가려진 연결" 지적이면 먼저 그 길이 `refs()`/`counted()`를 거치는지 볼 것(칸 안 `refs` 배열을 직접 쓰면 가려진 것까지 봄). 실행 취소로 겹침이 생기는 것 자체(`undone`)는 고치지 않기로 함(⚪). "다른 인물이 들어감·연결이 사라짐"은 고치고, 메뉴가 잠깐 남거나 닫히는 순서 같은 표시 문제는 ⚪ 추천. 고칠 땐 chipfield의 연결 이동·실행 취소(`moveRefs`·`undone`)는 건드리지 말고, 메뉴 쪽(누를 때 다시 읽기·닫는 때)에서 막기. 실행 취소: 지우기는 Chromium에서 Ctrl+Z 두 번으로 글·연결 복원 확인(두 자리 = 두 편집). 아이폰 흔들어 실행 취소는 미확인. 패널 공통 클릭 처리기는 메뉴 버튼에서도 끝에 작업 저장을 함(화면=저장본이라 문제 아님. 메뉴 버튼은 `data-pill-*`라 다른 분기에 안 걸림 — `data-profile` 같은 기존 이름은 쓰지 말 것).
- **알약 줄(0.1.153) 지적이 나오면:** 알약은 `field.refs()`를 읽기만 함. "알약이 실제 연결과 어긋남" 지적이면 먼저 그 길이 `input`이나 `ncs-field-set`을 보내는지(값을 코드로 넣는 곳은 setter가 보냄), 프로필 변경이 `renderProfiles`를 지나가는지 볼 것. 고칠 땐 chipfield.mjs 연결 처리는 건드리지 말고 다시 그리는 때만 더하기. 표시만 잠깐 늦는 건 ⚪ 추천.
- **"원문이 바뀐 작업" 지적이 나오면(0.1.142 A안):** 화면에서 칸을 비우는 해결은 다시 넣지 말 것(그게 화면≠저장본 문제의 뿌리). 바뀐 원문은 **추출 시작(`extract`, `TARGET_CHANGED`)** 한 곳에서 멈춤. 다른 길(이 요청으로 다시 추출은 `extract` 거침, 생성은 이미 추출된 장면을 씀, 이력 가져오기는 기록의 장면)이 바뀐 원문을 쓰는지 지적되면 먼저 그 길이 `extract`를 지나가는지 볼 것. 다시 고르기가 늘어나는 불편은 ⚪.
- **"추가 요청이 다른 메시지로 감" 지적이 또 나오면(0.1.143~0.1.148):** 지금 지키는 곳 — ⓪ 고르는 길은 둘뿐: 대상 목록 줄(`target-message`, 줄의 `data-message-mark`를 `chooseTarget`에 넘김 → 다르면 `TARGET_STALE`)과 메시지 옆 그림 버튼(`drawFromMessage`, 클릭 때 키·지문 + 최신 누름 확인 두 번: 패널 열린 직후·챗샷 전환 뒤). 이력·확대 보기에서 가져오기는 ⑥ 길(확대 보기 보내기는 기다림 뒤 `drawPress` 비교, 0.1.150. 확대 보기 [본문에 넣기]는 작업을 바꾸지 않고 첨부 창만 엶 — `viewerAttachPress`·열린 창 확인, 0.1.151~0.1.152). [가장 최근 메시지](`target-latest`)는 값 ''. ① `chooseTarget`: 다른 번호면 추가 요청 비움, 고를 수 없는 번호면 `TARGET_MISSING`(바꾸지 않음), mark가 다르면 `TARGET_STALE`(바꾸지 않음), 고르면 `draftSource`=그 메시지 지문 ② `renderTargets`: 빈 본문이면 대상 유지, 없어진 번호는 추가 요청이 빌 때만 가장 최근(+`draftSource=null`), 라벨은 `isSceneMessage` 기준 ③ `extract` 시작: 추가 요청이 비면 `renderTargets()` → `TARGET_CHANGED`(대상 있음 + `draftSource` 지문 불일치) ④ `extract` 반복문: 재시도 전 `startTarget`·`sourceValid(selection.source)`·추가 요청 같음(0.1.146) ⑤ 결과 적용 직전: `sourceValid`·추가 요청 같음·`startTarget` 같음 ⑥ `importHistory`(같은 채팅): 추가 요청은 그림의 원래 대상·지문과 함께, 모르면 비움 ⑦ `chatChanged`: 다른 채팅이면 대상·추가 요청 비움, 같은 키면 `renderTargets()`. 새 길이면 이 중 가장 가까운 곳에서 같은 확인을 쓸 것. `draftSource`가 null이면 `TARGET_CHANGED`가 안 걸린다는 점 주의(0.1.145 P2-1의 원인). 남은 ⚪: 이전 보내기의 오류 안내(0.1.150 P3), 이전 [본문에 넣기]의 조회 실패 안내(0.1.152 P3), 불러오는 중 그림 버튼 다시 누르기(0.1.149 P3), 본문·스와이프까지 같은 메시지(0.1.143 P2-2), 다시 만든 그림의 대상 기록(0.1.144 P3), 리롤 뒤 다시 고르기, 불러오기 안내 순서(0.1.145 P3), 스트리밍 중인 줄의 `TARGET_STALE` 반복(0.1.146 P3).
- **"불러오는 틈" 지적이 또 나오면:** 그 경로가 `workKey()`(화면 채팅)/`keyOf()`(실리태번 지금 ID) 중 무엇을 쓰는지, `chatLoading()` 확인을 지나가는지부터 볼 것. 지금 확인이 있는 곳: `assertChat`·`withChatWrite`·`deleteImages`·`importHistory`(챗샷)·`renderTargets`·`chooseTarget`·target-more·`bind-card`·태그 팝업·`goToMessage`·`resetImageOutfit`(기본 복장 입기)·`saveToWardrobe`·`missingAction`·`editFinalField`(직접 수정 없을 때)·`#ncs-final` JSON 입력(직접 수정 없을 때, 0.1.141), `recallDraft`는 불러오는 중·빈 본문이면 원문 안내 생략. 이력은 전체 삭제 버튼·[더 보기]·확대창 모두 `historyShown`. 아직 `keyOf()`/`outfitState()`를 직접 쓰는 후보(지금은 화면 표시만): `loadHistory`(첫 읽기 키 `keyOf()`, 반영은 `stale()`), `lastLink`·`pendingBind`(chatKey 비교만), 태그 팝업 표시(`renderTagPopupSetting`), 인물 카드 복장 표시(`outfitNow`·`renderScene`의 `outfitState()`, 1518·1633줄 근처 `sourceValid(...,ctx().chat)` 표시), 최종 프롬프트 표시(`updateFinal`→`assembleScene`) — 전환 중 잠깐 B 복장으로 보일 수 있음(`finalText`로 저장은 되지만 `finalOverride`가 없으면 불러올 때·비교 때 안 씀, 0.1.142). 지적되면 표시만이면 ⚪ 추천.
- **"옛 그룹 키" 지적이 또 나오면:** 비교는 `sameChat()`, 서버로 보내는 키(삭제·조회)는 그 기록의 실제 키. 서버의 "이 채팅" 범위·채팅별 목록은 정확한 키라서 옛 키 그림은 "모든 채팅"에만 나옴(⚪ 알려진 한계, 서버를 바꾸거나 키를 옮기지 않기로 함). 새 길이면 가장 가까운 공통 지점에 같은 확인. 정상 전환·채팅 없는 상태에서 확인이 잘못 걸려 막히는지도 볼 것(0.1.138부터 chatKey ''도 비교함).
- **"전체 삭제가 꺼진 채 남음" 지적이 나오면:** `historyShown`을 바꾸는 곳은 `loadHistory` 반영과 ★ 실패 복원 두 곳뿐. 목록을 비우는 다른 곳(scope 바꾸기, chatChanged 등)은 그대로 두고, 다음 `loadHistory`가 맞춤.
- 지운 그림·작업 저장 쪽 지적이 또 나오면: 지금 거르는 곳은 `loadWork`(화면에 올릴 때), `rememberDraft`(줄에 넣을 때·화면에서도 뺌), `write` 콜백(전송 직전), `loadHistory`(응답 반영·더 보기 시작·요청 중 삭제면 응답 버리고 다시 읽기, 그때 저장 대기도 정리), 확대창 `historyGallery.loadMore`(offset 당김), `putImagesInChat`(채팅 저장 직전), ★·# 실패 복원, `importHistory`(두 번), `checkGeneration`·`generate` 완료. 새 길이면 이 중 가장 가까운 공통 지점에서 막을 것.
- "삭제 중·떠날 때 저장 안 됨" 지적이 또 나오면: 그 기능이 `scheduleDraft`/`rememberDraft`를 부르는지 확인(패널 클릭은 공통 처리기 끝에서 화면 전체 저장 — 삭제 버튼은 **삭제가 끝난 뒤** 저장, 입력은 `input` 처리기의 finally에서 `scheduleDraft`, 파일 선택·패널 밖 버튼은 따로 불러야 함). 작업 삭제(`whileDeletingWork`)는 멈추기 전에 예약·줄의 편집을 모두 보내고, **지우는 작업(keys)만** 멈춤(전체 삭제는 모두). 채팅 전환 중 저장은 `switchingChat`이 막음. 0.1.134 한계 후보: 한 작업만 멈춘 동안 다른 작업 저장이 지우는 중인 그림을 담고 갈 수 있음(드묾) — 지적되면 ⚪ 추천.

## 2. 실리태번 채팅 전환 순서 (불러오는 틈)

실리태번 `public/script.js`에서 확인(0.1.137). 비교용으로 받을 땐 `SillyTavern/SillyTavern` main을 sparse clone.

- `selectCharacterById`: `setCharacterId(undefined)` → `clearChat({clearData:true})`(**`chat.length=0`**) → `setCharacterId(id)` → `chat_metadata={}` → `await getChat()`.
- `openCharacterChat(file)`: `clearChat({clearData:true})` → `characters[this_chid].chat=file` → `chat_metadata={}` → `getChat()`.
- `getChat()`: fetch → `chat_metadata` 채움 + `chat.splice(…data)` → `integrity` 없으면 만듦 → `getChatResult()`(새 채팅이면 인사말 push·저장 → `printMessages` → **`CHAT_CHANGED`**) → `CHAT_LOADED`.
- 그래서 틈은 두 단계: ① 채팅이 빈 채로 ID만 B(본문 받는 중) ② B 본문이 들어왔지만 `CHAT_CHANGED` 전.
- 검사 fixture의 `mock.switchChat`은 이 틈이 없음 → 틈 흉내는 `mock.chatId=id;mock.characters[0].chat=id`(이벤트 없이, ①이면 `mock.chat=[]`도) 뒤 나중에 `mock.switchChat(id)`. fixture의 `chatMetadata`에는 `integrity`가 없음(그래서 integrity로 틈을 판단하면 옛 검사가 깨짐 — 0.1.137에서는 `chat.length`로 판단).

## 3. 작업 기억 구조 (리뷰 때 볼 곳)

- **두 약속:** ① 서버 저장본으로 화면을 바꾸기 전에 비교하고 다르면 묻기 ② 서버와 비교해 본 적 없는 작업은 서버에 쓰지 않기.
- **원문 검사(0.1.142~0.1.148):** 대상·추가 요청이 새는 길 정리는 1절 "추가 요청이 다른 메시지로 감"의 ⓪~⑦. `recallDraft`는 `sourceChanged()`(= `scene.source`나 `draftSource`가 `ctx().chat`과 안 맞음)를 `!isFree()&&!chatLoading()&&본문 있음`일 때만 보고, **안내(`STALE_NOTE`)만** 띄움 — 칸은 비우지 않음. 고른 대상이 바뀐 걸 막는 곳은 `extract` 시작(`TARGET_CHANGED`) 한 곳.
- **작업 키:** `workKey()` = `isFree()?FREE_KEY:chatKey`(0.1.136). `chatKey`는 화면에 불러온 채팅(시작 때 `keyOf()`, `chatChanged`가 바꿈). `keyOf()`는 실리태번 지금 ID. 프리샷 키 `JSON.stringify({free:true})`. 채팅 키 `JSON.stringify({group:null,card:'Leo.png',chat:'A'})` 꼴.
- **채팅 전환:** `chatChanged()` — `key===chatKey`면 끝. 아니면 옛 키로 `leaveSave()`(0.1.141, 저장 예약된 편집만) → `chatKey=key` → (프리샷이면 spare.chat 비우고 끝) → `switchingChat`(0.1.135) 켠 채 추출 취소 → 화면·이력 비우고 `recallDraft()`. `open()`은 0.1.137부터 `chatLoading()&&!ctx().chat?.length`면 `chatChanged()`를 건너뜀. `CHAT_CHANGED` 처리기: `chatLoadEpoch++;noteTimed();chatChanged();`(패널 닫혀 있어도 돎).
- **불러오는 틈 막기(0.1.137):** `chatLoading()`·`CHAT_LOADING` — `assertChat`, `withChatWrite`, `deleteImages` 시작, `importHistory`(챗샷).
- **불러오기는 `recallDraft(key,{connect,asked})` 하나.** 화면이 비어 있지 않고 저장본과 다르면(`compareForm`) 물음, 취소면 `holdDrafts`(탭 보류). 삭제 기록(`entry.deleted`)이면 "서버에 이 작업의 삭제 기록이 있어요…". 불러온 작업의 원문이 바뀌었으면 안내만(0.1.142부터 비우지 않음, 그 전엔 화면에서만 비워서 저장 길마다 지적이 나왔음).
- **화면 밖 작업은 다시 저장하지 않음.** `unsavedWork(key,w)`: 'dropped'/'failed'/false로 안내 두 가지.
- **생성 완료:** `generate`가 `startedConnected`, `generationDraft`, `startGen`을 기억. `sameWork()`가 아니면 결과는 이력에만. 요청은 `requestParts()` 한 곳에서 조립(work: `workKey()`).
- 손대지 않은 것: 작업 삭제 보호(`holdDraftDeletion`, `reconcileDraftDeletion`, `forgetWork`), `connectingDrafts`.
- **그림 삭제와 작업:** `deleteImages`는 끝에 채팅과 상관없이 `renderResult()`, 삭제된 이력 카드는 바로 뺌. 확인된 삭제 ID는 `deletedPictures`(Set) + localStorage `naice-shot-deleted-pictures`(최근 500개, 같은 브라우저 다른 탭도 앎, `isDeletedPicture`가 매번 다시 읽음, `keepDeletedPictures`). `loadWork`가 `withoutDeleted()`로 result·undoClear.result를 뺀 뒤 바뀌었으면 true → `recallDraft`가 **저장본에서 그림만 뺀 것**을 다시 저장(화면 저장 아님). 삭제 때 `spare`(다른 모드 대기 작업)와 지금 `undoClear`도 정리하고 저장. 서버는 작업 기억 속 그림을 정리하지 않음(다른 브라우저·기기 삭제는 ⚪). 이력 가져오기는 모드 전환 뒤에도 삭제 확인, ★·# 실패 복원도 지운 그림을 뺌.
- **패널 공통 클릭 처리기:** 끝에서 작업 저장. `moves`(자리만 옮기는 클릭 — `data-tab`, 이미 고른 `data-mode`, `data-historyScope`, `data-profileMode`)는 저장 안 함.

- **작업 삭제(`whileDeletingWork(keys,…)`):** 멈추기 전에 예약된 편집과 줄에서 기다리는 편집을 모두 `drafts.flush`(loaded·dirty·전송 중 아님·409 아님). 줄은 **지우는 작업만** 멈춤(draft-work.mjs `pause(keys)`가 `pausedKeys`를 기억, `stopped(key)` = paused && (pausedKeys 없음 또는 포함) || held, put·flush·저장 반복문에서 씀). `paused` 자체는 true(그리기창 잠금 `workLockedFor`·두 번째 삭제 거절에 씀). index.js `deletingKeys`(keys로 설정, finally에서 null), `rememberDraft`는 `pauseDraftCapture&&!(deletingWork&&deletingKeys&&!deletingKeys.includes(key))`일 때만 막음. `pauseDraftCapture`는 작업 삭제만 켜고 끔. 같은 작업 저장이 이미 전송 중이면 새 편집은 삭제 끝까지 줄에 남음(⚪).
- **작업 모두 지우기(`deleteAllWork`):** 시작 목록 `keys`(drafts.entries+workKey+chatKey+FREE_KEY), 성공 때와 응답 유실 뒤 확인 때 모두 목록을 다시 모음(0.1.136·0.1.137).
- **이력:** `loadHistory({append})` — 다시 읽어야 하면(`reread`) 그 응답을 반영하지 않고 지운 카드만 빼고 `historyHasMore=true`로 `renderHistory()` 뒤 다시 읽음, 그때 삭제 확인된 저장 대기 항목도 빼고 `pendingBytesOf`로 용량 재계산. [더 보기] 시작에서 지운 카드 빼고 남은 장수를 offset으로. 확대창 `historyGallery.loadMore` offset 당김(`counted` Set + `uncount`). 오류 알림은 `notice(msg,true,'history')`.
- DraftQueue(draft-work.mjs): 저장 예약 450ms, 줄 지연 650ms, `write` 콜백(전송 직전)에서 `withoutDeleted`.

## 5. 아이폰 시험 페이지 (아이폰 문제 조사 방법)

- 크로미움(Playwright)은 아이폰 사파리를 재현 못 함(웹킷 없음). 사파리·파이어폭스가 값을 코드로 넣을 때 실행 취소 기록을 남기는지는 미확인(크로미움: 같은 값이면 남고 다른 값이면 지움. HTML 표준에도 규정 없음 — GPT 확인). 아이폰 문제는 **확장 코드를 묶은 단독 HTML 페이지를 아티팩트로 올리고 사용자가 아이폰 Claude 앱에서 열어** 칸마다 ✅/❌ + 이벤트 기록을 [결과 복사]로 받아 옴.
- 묶는 법: 작은 node 스크립트로 `matching.mjs`·`mentions.mjs`·`chipfield.mjs`(필요하면 더)를 `const M_x=(()=>{…;return {exports};})();` 꼴로 이어 붙이고(import는 `const {…}=M_from;`, core는 `clone`만), 시험 HTML 머리 + 묶음 + 꼬리 스크립트로 한 파일. 실제 패널 모양이 필요하면 `panel.html`·`style.css`를 그대로 넣고 `<dialog id="naice-shot-dialog">`로 띄움. 먼저 크로미움으로 페이지가 도는지 확인 후 publish_files.
- 알아낸 것(iOS 18.7 사파리·Claude 앱 같은 결과):
  - 아이폰 한글 키보드는 **compositionstart/end가 없음**. 글자마다 "치던 낱말 길이만큼 `deleteContentBackward` → 낱말 전체 `insertText`". 그 낱말을 키보드가 기억해서, 칸 글을 코드로 바꿔도 다음 글자에서 옛 낱말 기준으로 지우고 넣음. **키보드를 실제로 닫으면(blur) 잊음.**
  - contenteditable 칩 칸은 단독 페이지에선 입력되는데 실리태번 안에서는 커서가 안 떴음(원인 미상).
